# Heartbeat

**Service and Infrastructure Monitoring Platform**

Heartbeat is a lightweight, extensible monitoring platform designed to track the health and availability of external services such as PostgreSQL databases, Redis instances, REST APIs, and websites.

The initial use case focuses on monitoring services hosted on platforms such as Aiven. Heartbeat performs scheduled health checks, records service health and response times, detects incidents after repeated failures, and notifies users when services become unavailable or recover.

The platform is intentionally designed to remain small and maintainable while providing a foundation for future monitoring, analytics, notification, and infrastructure features.

---

## Features

### Core Monitoring

* **Automated Health Checks** - Periodic monitoring using configurable check intervals.
* **Real-Time Status** - Current health status for every monitored service.
* **Incident Detection** - Creates incidents after three consecutive health-check failures.
* **Response Time Tracking** - Records health-check response times in milliseconds.
* **Health History** - Maintains historical health-check records and failure information.
* **Service Recovery Detection** - Automatically detects when a failed service becomes healthy again.

### Service Management

* **Multi-Service Support** - PostgreSQL, Redis, MySQL, REST APIs, and websites.
* **Provider Support** - Aiven, AWS, GCP, Azure, and self-hosted services.
* **Encrypted Credentials** - Sensitive service credentials are encrypted at rest using Fernet symmetric encryption.
* **Monitoring Controls** - Monitoring can be enabled or disabled independently for each service.
* **Connection Testing** - Users can verify service connectivity before enabling monitoring.

### Notifications

* **In-App Notifications** - Displays incidents and recovery events inside the application.
* **Email Alerts** - Sends email notifications for important service events.
* **Recovery Alerts** - Notifies users when a previously unavailable service recovers.
* **Notification Preferences** - Allows users to control how they receive alerts.
* **Notification History** - Maintains a record of notifications generated by the system.

### User Experience

* **Modern Interface** - Dark-themed interface with a clean monitoring-focused design.
* **Responsive Design** - Supports desktop, tablet, and mobile layouts.
* **Skeleton Loading States** - Provides visual feedback while data is loading.
* **Collapsible Sidebar** - Provides efficient navigation across the application.
* **Service Dashboard** - Provides an overview of service health and active incidents.

### Security

* **Token Authentication** - Secures API access.
* **Credential Encryption** - Sensitive service credentials are encrypted before being stored.
* **Password Hashing** - User account passwords are hashed using Django's password hashing system.
* **SSL/TLS Connections** - Supports secure connections to monitored services where required.
* **User Isolation** - Users can access only their own services, health checks, incidents, and notifications.
* **Environment-Based Secrets** - Encryption keys and application secrets are kept outside the database.

## Architecture Responsibilities

### Django

Django is the main application layer.

It provides:

* Authentication
* Service management
* REST API
* Dashboard backend
* Health endpoint
* Incident management
* Notification management

### Celery

Celery handles background and asynchronous tasks.

Examples include:

* Running health checks
* Sending email notifications
* Processing monitoring jobs
* Performing other long-running operations

### Celery Beat

Celery Beat is the scheduler.

It determines when monitoring tasks should be executed.

For example:

```text
Every 5 minutes
       |
       v
Check enabled services
       |
       v
Create monitoring tasks
```

### Redis

Redis acts primarily as the Celery message broker.

It provides a temporary queue through which scheduled tasks are passed from Celery Beat to Celery Workers.

```text
Celery Beat
     |
     | Monitoring task
     v
   Redis
     |
     | Task waiting
     v
Celery Worker
     |
     v
Health Check
```

Redis may also be used as Django's caching backend in future versions.

These are separate responsibilities:

```text
Redis
 |
 +-- Celery message broker
 |
 +-- Django cache
```

### UptimeRobot

UptimeRobot provides external monitoring for Heartbeat itself.

Heartbeat exposes:

```text
GET /health/
```

UptimeRobot periodically requests this endpoint.

This creates two levels of monitoring:

```text
UptimeRobot
     |
     v
Heartbeat
     |
     v
External Services
```

UptimeRobot monitors Heartbeat, while Heartbeat monitors the services configured by its users.

# Monitoring Lifecycle

A monitored service follows a simple lifecycle.

```text
                 +----------+
                 | Healthy  |
                 +----+-----+
                      |
                Failed checks
                      |
                      v
                +-----------+
                |  Failure  |
                | Threshold |
                +-----+-----+
                      |
              3 consecutive
                 failures
                      |
                      v
                +-----------+
                |  Incident |
                |   Open    |
                +-----+-----+
                      |
                 Service
                  recovers
                      |
                      v
                +-----------+
                |  Incident |
                |  Resolved |
                +-----------+
                      |
                      v
                 Healthy
```

A single failed check does not immediately create an incident.

For example:

```text
Check 1    SUCCESS
Check 2    SUCCESS
Check 3    FAILURE
Check 4    SUCCESS
```

The service remains healthy.

However:

```text
Check 1    FAILURE
Check 2    FAILURE
Check 3    FAILURE
```

creates an incident.

The failure threshold can be made configurable as the project evolves.

# Notifications

Heartbeat separates incident detection from notification delivery.

The monitoring system determines that something happened:

```text
Service unavailable
```

The notification system determines how the user should be informed:

```text
                    Incident
                       |
                       v
                Notification System
                       |
              +--------+--------+
              |                 |
              v                 v
           In-App             Email
```

Future notification channels may include:

* SMS
* WhatsApp
* Telegram
* Push notifications

Notifications are handled asynchronously through Celery where external services are involved.

# Security and Credential Management

Heartbeat handles two fundamentally different types of credentials.

## User Account Passwords

User passwords are never encrypted for later retrieval.

They are securely hashed using Django's password hashing framework.

```text
User Password
      |
      v
Password Hashing
      |
      v
Database
```

The original password cannot be retrieved by the application.

## Service Credentials

Credentials required to connect to monitored services must be recoverable by the monitoring system, so they cannot be stored as one-way hashes.

Sensitive service credentials are encrypted using Fernet symmetric encryption.

```text
Service Credential
       |
       v
    Encrypt
       |
       v
Encrypted Value
       |
       v
Database
```

When a monitoring task executes:

```text
Encrypted Credential
       |
       v
     Decrypt
       |
       v
Credential in Memory
       |
       v
Connect to Service
       |
       v
Perform Health Check
```

The encryption key is not stored in the database.

It is supplied through the application's environment or a dedicated secret-management system.

Where possible, users should provide dedicated monitoring credentials with only the permissions necessary to perform health checks.

# Getting Started

## Prerequisites

* Python 3.12+
* Node.js 18+
* Redis
* PostgreSQL
* Git

An Aiven account is required if Aiven services are being used for monitoring or database hosting.

---

## Clone the Repository

```bash
git clone https://github.com/yourusername/heartbeat.git
cd heartbeat
```

---

# Backend Setup

```bash
cd backend

python -m venv .venv
```

Activate the virtual environment.

### Linux/macOS

```bash
source .venv/bin/activate
```

### Windows

```powershell
.venv\Scripts\activate
```

Install dependencies:

```bash
pip install -r requirements.txt
```

Create the environment file:

```bash
cp .env.example .env
```

Configure the environment variables in `.env`.

Generate a Fernet encryption key:

```bash
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Store the generated key in the environment configuration.

Run migrations:

```bash
python manage.py migrate
```

Create an administrator:

```bash
python manage.py createsuperuser
```

Start Django:

```bash
python manage.py runserver
```

---

# Frontend Setup

From the project root:

```bash
cd frontend
```

Install dependencies:

```bash
npm install
```

Create the local environment configuration:

```bash
echo "VITE_API_URL=http://localhost:8000/api" > .env
```

Start the development server:

```bash
npm run dev
```

# Design Philosophy

Heartbeat follows a simple engineering principle:

> **Small enough to build, structured enough to grow.**

The first version focuses on one reliable monitoring loop:

```text
Register
   |
Add Service
   |
Schedule Check
   |
Perform Health Check
   |
Record Heartbeat
   |
Detect Failure
   |
Create Incident
   |
Notify User
   |
Detect Recovery
   |
Resolve Incident
```

The system should not attempt to implement every monitoring feature from the beginning.

Instead, each component should have a clear responsibility so that future capabilities can be added without rewriting the core system.
